## Задание

### Задача

В компании два офиса: Москва (Europe/Moscow) и Новосибирск (Asia/Novosibirsk), в каждом есть переговорные. Предыдущий разработчик написал API бронирования, и пользователи жалуются на ошибки. Код — в `app/Http/Controllers/BookingController.php`.

### Часть 1. Ревью

### Часть 2. Доработка

Исправьте `store` и `destroy` так, чтобы выполнялись правила:

- Брони одной комнаты не пересекаются. Встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 — это не пересечение.
- Длительность от 15 минут до 4 часов, шаг 15 минут (10:00, 10:15…).
- Бронь целиком укладывается в рабочее время 09:00–20:00 по местному времени офиса, где находится комната. Клиент присылает время в ISO 8601 с любым смещением.
- Отменить бронь может только её автор.
- Понятные ошибки валидации (422).
- Других ограничений на даты нет.
- Feature-тесты на все правила выше.

Можно менять модели и миграции и добавлять свои классы. Методы `index` и `today` исправлять не нужно, их достаточно разобрать в ревью.

Бонус: при двух одновременных запросах на один слот может создаться двойная бронь. В основной части достаточно, чтобы брони не пересекались при последовательных запросах. Гонку исправьте или опишите в README, как бы вы это сделали.

## Запуск

Нужны Docker и Docker Compose.

Команды выполняются из корня репозитория. `migrate:fresh --seed` удаляет таблицы настроенной базы: используйте только выделенную учебную БД `booking` из Compose, не подключайте production-базу.

```sh
docker compose up -d --wait
docker compose exec app php artisan migrate:fresh --seed
```

Первый запуск занимает несколько минут: контейнер устанавливает зависимости из `composer.lock`. API доступно по адресу `http://localhost:8000/api`; порт опубликован только на `127.0.0.1`. Если ваш UID/GID отличается от 1000, запустите первую команду как `env UID="$(id -u)" GID="$(id -g)" docker compose up -d --wait`.

## Тесты

```sh
docker compose exec app php artisan test
```

Тесты идут на PostgreSQL в отдельной базе `testing`, которая создаётся при первом запуске нового тома PostgreSQL. Эта база очищается тестами. При старом томе без `testing` создайте её: `docker compose exec postgres createdb -U booking testing`.

Feature-тесты проверяют правила бронирования, авторизацию, попытки подмены автора и SQL-инъекции. Тест гонки запускает два отдельных PHP-процесса с настоящими HTTP-запросами через Laravel kernel и отдельными соединениями с PostgreSQL. Он дожидается блокировки обоих запросов и проверяет ответы 201/422 и единственную запись. Это не сетевой нагрузочный тест. Используйте выделенную базу `testing`; параллельный запуск всего набора (`--parallel`) не настроен.

## Реализация

- [REVIEW.md](REVIEW.md) — ревью исходной версии с серьёзностью проблем и предлагаемыми исправлениями, включая `index` и `today`.
- [AI_NOTES.md](AI_NOTES.md) — использованные инструменты, промпты и проверка предложений ИИ.
- `StoreBookingRequest` проверяет поля, даты и бизнес-правила; `BookingPolicy` разрешает удаление только автору. `index` и `today` оставлены для ревью без изменения поведения.
- Автор берётся из токена. Переданный клиентом `user_id` игнорируется; достаточно передать `room_id`, `title`, `starts_at`, `ends_at`.
- Даты принимаются в расширенной календарной записи ISO 8601: `YYYY-MM-DDTHH:mm[:ss[.ffffff]]` с обязательным `Z` или числовым смещением `±HH:mm`, `±HHmm`, `±HH`. Невозможные даты и относительные строки отклоняются. Сетка 15 минут проверяется после перевода в часовой пояс офиса; секунды и доли секунды должны быть нулевыми.
- Обе границы сохраняются в UTC в существующих колонках `timestamp without time zone` и возвращаются как ISO 8601 в UTC. Для этих колонок действует конвенция UTC; старые записи с неизвестным исходным смещением не переинтерпретируются автоматически.
- Длительность — 15–240 минут включительно. Вся встреча находится в пределах 09:00–20:00 одного местного дня. Прошедшие даты, выходные и будущие даты разрешены.
- Создание возвращает 201; ошибки полей и занятый слот — 422 с `message` и `errors`; удаление — 204, чужая бронь — 403, отсутствующая — 404; без токена — JSON 401, в том числе без `Accept`.

### Защита от двойной брони

В транзакции PostgreSQL сначала выполняется `SELECT ... FOR UPDATE` по строке комнаты, затем проверка пересечения и вставка. Блокировка комнаты работает даже тогда, когда броней ещё нет. В стандартном `READ COMMITTED` второй запрос после ожидания увидит запись первого. Разные комнаты не сериализуются этой блокировкой. Соседние интервалы разрешены: пересечение проверяется строгими `<` и `>`.

Гарантия действует для создания через этот API: другие писатели тоже должны брать ту же блокировку. Для гарантии на уровне БД можно добавить `btree_gist` и `EXCLUDE USING gist (room_id WITH =, tsrange(starts_at, ends_at, '[)') WITH &&)`, предварительно очистив существующие пересечения; нарушение ограничения нужно преобразовывать в 422. Для текущего задания расширение PostgreSQL не требуется. Если в будущем появится перенос/изменение брони, он также должен использовать блокировку комнаты (при переносе — обеих комнат в стабильном порядке).

## API

Все методы требуют заголовок `Authorization: Bearer <токен>`. `Accept: application/json` рекомендуется; ошибки `api/*` возвращаются в JSON и без него. Для JSON-тела нужен `Content-Type: application/json`.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Лог созданных броней пишется в `storage/logs/bookings.log`.

При реализации использовалась официальная документация Laravel 13: [Form Requests](https://laravel.com/framework/docs/13.x/validation#form-request-validation), [pessimistic locking](https://laravel.com/framework/docs/13.x/queries#pessimistic-locking), [policies](https://laravel.com/framework/docs/13.x/authorization#creating-policies). Установленные версии проверены через `composer show --direct`: Laravel 13.39.0, Sanctum 4.3.3, PHPUnit 12.5.42.
