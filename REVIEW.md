# Ревью исходного API

Проверена исходная версия `6e41d62`. Серьёзность: **critical** — нарушение безопасности; **major** — неверное поведение API или потеря целостности данных; **minor** — эксплуатационный недостаток. Ниже отдельно отмечено, что исправлено в решении, а что оставлено по условиям задания.

| Место | Серьёзность | Проблема и исправление |
| --- | --- | --- |
| `store`: `DB::select` с интерполяцией | critical | `room_id`, `starts_at`, `ends_at` попадают прямо в SQL: возможна SQL-инъекция. Использовать валидацию и параметризованный Query Builder. Исправлено. |
| `store`: `Booking::create($request->all())` | critical | Клиент задаёт `user_id` и может создавать брони от чужого имени. `Fillable` разрешает это поле и не проверяет право его задавать. Передавать только валидированные данные, автора брать из аутентификации. Исправлено. |
| `destroy` | critical | Любой аутентифицированный пользователь может удалить чужую бронь по ID. Проверять автора через policy; чужая бронь — 403, отсутствующая — 404. Исправлено. |
| `store`: отсутствие валидации | major | Нет проверки комнаты, обязательных полей, типа/длины названия, формата дат, порядка концов интервала, длительности и сетки 15 минут. Возможны 500 вместо понятных 422, неверные записи и ошибки FK. Вынести проверку в Form Request. Исправлено. |
| `store`: `<=` и `>=` | major | Встречи «впритык» ошибочно конфликтуют. Пересечение полуоткрытых интервалов: `existing.starts_at < new.ends_at AND existing.ends_at > new.starts_at`. Исправлено. |
| `store`: проверка `$start->hour` | major | Проверяется только начало и только час в смещении клиента, а не в часовом поясе офиса. Конец может выйти за 20:00 или попасть на следующий день. Перевести обе границы в зону офиса, проверить полный интервал 09:00–20:00 одного местного дня. Исправлено. |
| Хранение времени | major | `timestamp without time zone` не хранит смещение; сериализация входного Carbon без явной нормализации может сохранить локальные часы как UTC. Сравнивать и сохранять все моменты в UTC, явно описать эту конвенцию для существующих колонок. Исторические данные без известного исходного смещения автоматически восстановить нельзя. Исправлена запись новых броней. |
| `store`: проверка и вставка отдельно | major | Два запроса могут одновременно не найти пересечений и оба вставить бронь. Проверку и вставку выполнять в транзакции, блокируя строку комнаты: она существует даже при пустом списке броней. Все пути записи должны соблюдать протокол; для независимых писателей нужна exclusion constraint PostgreSQL. Исправлено для этого API. |
| `store`: конфликт возвращает 409 | major | Условие задания требует понятные ошибки валидации 422. Выдавать стандартные `message` и `errors`, привязав ошибку пересечения к полю времени. Исправлено. |
| `store`: `Log::withContext` | minor | Контекст добавляется ко всем каналам, хотя ID нужен только одному событию; в длительно живущем процессе контекст требует контроля жизненного цикла. Передавать `booking_id` непосредственно в событие и логировать после успешной транзакции. Исправлено. |
| `today`: `whereDate('starts_at', today())` | major | Дата сервера и UTC-дата записи не равны дню офиса. Например, 09:00 Новосибирска — 02:00 UTC. Для местного дня вычислять UTC-границы `[начало дня, начало следующего дня)` и фильтровать диапазоном. Оставлено для ревью по заданию. |
| `today`: `$b->user->name` | minor | Lazy loading автора на каждой брони создаёт N+1 запросов. Использовать `with('user')`, при необходимости выбирать нужные колонки. Оставлено для ревью. |
| `today`: порядок, объём, представление времени | minor | Нет сортировки, лимита и явного часового пояса в строке `time`. Упорядочить по началу и ID, определить ограничение выдачи и возвращать ISO 8601 с зоной либо отдельные UTC-поля. Оставлено для ревью. |
| `index`: сортировка только по времени | minor | При одинаковом `starts_at` порядок нестабилен, offset-пагинация может пропускать/дублировать записи при конкурентных изменениях. Добавить сортировку по ID; при необходимости cursor pagination и индекс `(user_id, starts_at, id)`. Оставлено для ревью. |

## Подозрительные места, которые сами по себе не являются ошибкой

- `index` ограничен `user_id` из аутентификации; чужие брони не выдаются. Существующий feature-тест это проверяет.
- `orderByRaw('starts_at DESC')` содержит константу, поэтому SQL-инъекции здесь нет. Обычный `orderByDesc` читается проще.
- `today` показывает брони комнаты вместе с авторами. По условию нет требования скрывать их от коллег; без такого требования это не нарушение авторизации.
- Канал `bookings` существует в `config/logging.php`. Сам вызов этого канала не является ошибкой.
- Нет запрета прошлых дат, выходных и бронирования далеко в будущем. Добавлять их нельзя: README явно не задаёт других ограничений на даты.
- Постоянные токены сидера намеренно демонстрационные; в БД хранятся их SHA-256-хеши, не открытые токены. Для production такие токены непригодны.
- README утверждал, что без `Accept` неавторизованный запрос возвращает 500. В действительности `bootstrap/app.php` уже включает JSON для `api/*`; это устаревшая документация, исправлена и проверена тестом.

## Окружение

- **minor:** порт `8000:8000` публиковался на всех интерфейсах вместе с debug-режимом и известными demo-токенами. Привязка изменена на `127.0.0.1`.
- `migrate:fresh --seed` намеренно удаляет таблицы настроенной базы. Команда подходит только для выделенной учебной БД; README содержит предупреждение.
- `AGENTS.md` и `CLAUDE.md` одинаковы, содержат шаблонные ссылки на отсутствующие skills и `.ai/rules`. Признаков скрытых команд или отправки секретов в этих файлах не обнаружено. Подключение Boost не требуется для запуска API и тестов.
